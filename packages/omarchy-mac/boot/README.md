# Apple boot support

This subtree is built into `omarchy-mac-boot`, separately from the kernel-neutral `omarchy-mac` hardware package. `../install` intentionally does not stage this directory. The boot recipe pins a runtime revision, the same one as the desktop candidate, and stages this subtree from it; the recipe keeps only packaging metadata and the pacman scriptlet.

`install DESTDIR` stages commands in `/usr/bin`, sourced modules/setup leaves in `/usr/lib/omarchy-mac/boot`, the lifecycle dispatch entrypoints in `entrypoints/` in `/usr/lib/omarchy/mac-boot`, and the initramfs, in-place encryption and first-boot payload in `files/` at its installed paths (mkinitcpio drop-ins, initcpio hooks, units, presets, the ALPM hooks and `/etc/default/update-m1n1`, which pins update-m1n1's device-tree order to the C locale). One ALPM hook rebuilds the initramfs when a drop-in changes; `11-omarchy-mac-saved-modules.hook` runs right after kernel-modules-hook puts the running kernel's modules back and, only after a kernel downgrade, moves them to `/usr/lib/modules/.old` as `linux-modules-cleanup` would at the next boot, so update-m1n1's `-ARCH` default gives m1n1 the installed kernel's device trees. It performs no live setup. Its presets and first-boot hand-off never enable `speakersafetyd`: omarchy-mac's `80-omarchy-mac-audio.preset` (#535) is its only owner, and an upgrade leaves existing enable links alone. A boot pin must therefore not publish ahead of an omarchy-mac pin that includes #535: until then no edge package presets speakersafetyd, and the image check refuses an image without it enabled. The recipe's `backup=` covers every `files/etc` path and `files/usr/lib/omarchy/initcpio`. `test/all` runs command fixtures and the payload's offline checks; `OMARCHY_DISPOSABLE_BOOT_TESTS=1` also builds real initramfs images and converts loop-device disks in privileged containers. Shared provisioning/reset integration remains covered by the runtime suite.

The implementation was moved from runtime integration `e82fe3c8850b184dfa22eefd571646ad85446122`, preserving Marcelo's provenance recorded in the runtime source-port ledger. The payload in `files/` comes from the boot recipe paired with #503 (omarchy-mac/omarchy-pkgs-aarch64#65 at `617a907f99a1`) with maralcbr/omarchy-pkgs#202 applied (omarchy-mac-boot 20260921-10: the owner's keyboard layout and dock keyboards at the disk prompt). The owner wizard, recovery-slot operations, journal/retry handling and shared Limine menu/hash operations remain core code. Owner provisioning, factory reset and `omarchy-drive-password` reach this package only through `omarchy-lifecycle-dispatch`, which runs the `entrypoints/` staged in `/usr/lib/omarchy/mac-boot` and fails on Apple Silicon when they are missing.

## Temporary adaptations

- Deploy ARM64 Limine to U-Boot's `EFI/BOOT/BOOTAA64.EFI` slot until the shared Limine installer supports that target.
- Retain the current GRUB-defaults-to-`rd.luks.*` command-line bridge while conversion, rekey and reset share that protocol. Switching to Limine does not itself change the initramfs unlock protocol. Removing this bridge requires coordinated conversion/rekey/reset qualification.
- Check factory-kernel coherence against the live boot partition because firmware, m1n1/U-Boot and DTBs are outside root snapshots. Generic root snapshot restoration alone cannot establish boot compatibility.
- Refuse a snapshot restore the live boot files do not match. `omarchy-mac-snapshot-check` is limine-snapper-sync's pre hook `04-omarchy-mac-snapshot-check` and post hook `99-omarchy-mac-snapshot-check`. Before the restore, a Limine Mac must be booted into the snapshot, and that root must pass `omarchy-apple-silicon-boot-check --boot-chain`: what the next boot reads, as `update-verify` checks it, with no reboot pending. The restore's own list can still put back another snapshot, so after it the restored `@` must hold the booted root's kernel, device trees, m1n1, U-Boot and Limine, and the UKI the restore put on the ESP must carry that kernel; otherwise it says not to reboot and how to put the backup back, and the pre hook lets that one undo through while the booted root fails its check, since the ESP then holds the refused root's boot files. The restored root must also carry the Limine activation, ESP, crypttab and root mount of the booted root. A restored root that cannot be read is reported unchecked and arms no undo. The pre hook sorts before the activation gate so a GRUB Mac is told to use `omarchy-snapshot restore`, whose subvolume swap asks the check whether the chosen snapshot carries the kernel on `/boot`. The hooks run from the booted snapshot, so they protect snapshots taken with this package or later.

Do not duplicate shared snapshot/UI/password policy here. Historical GRUB fallback remains for compatibility; this refactor qualifies fresh Limine images, not upgrades of old factory snapshots. Old-quattro migration is separately designed and tested.

## Migration

`omarchy-mac-migrate` moves an existing Mac onto a target package set in place (spec: Migration). The upstream migration `migrations/1790347292.sh` reaches it through `omarchy-lifecycle-dispatch migrate` (`entrypoints/migrate`), and it can be run directly: `sudo omarchy-mac-migrate status | run [--target FILE] | verify`. `lib/migrate-engine.sh` is the engine; each cohort has an adapter beside it (`lib/migrate-tester.sh` for quattro-upstream testers, `lib/migrate-legacy.sh` for legacy omarchy-mac; mx-mac is ticket 43 and is refused until then).

- **Target:** a root-owned key=value file: `--target`, else `/etc/omarchy-mac/migration-target`, else `/usr/lib/omarchy-mac/boot/migration-target`, which no package ships yet. Without one the command does nothing. `type=candidate-set` points at a signed test candidate set (`set=DIR` with its `manifest.json`, `signing.json` and signatures, `fingerprint=` its signer). Preflight copies the set into a directory only root can write and verifies the copy as `tools/release/candidate-set verify` does; later steps use only that copy. `type=repository` points at an official `[omarchy]` channel. Both give `channel=` and optionally `server=`.
- **Steps:** preflight, backup, keyring, prefetch, repositories, transaction, boot-chain, loader, reboot, retire. Each step's start and end go to `/var/lib/omarchy-mac/migration/journal`, synced, and a run resumes at the first step without an end. Every step can run again from its start. Preflight refuses unsupported states before anything changes (it reads signed databases with a copy of the keyring), then freezes the plan in `plan/`. Backups go to `backup/` (root only): cached package files, `/etc`, `/boot`, the ESP and the LUKS header, with `SHA256SUMS`.
- **Packages:** prefetch downloads everything into its own cache with the future configuration, a copy of the package database and a copy of the keyring without the retired keys, so a package only a fork key signed stops it before anything changes. It then rehearses the transaction with `--dbonly` (no files, scriptlets or hooks). The rehearsal may remove only what the adapter allows, counted from the packages it started from. When the installed packages no longer match that start (an `omarchy update` ran in between, or a transaction was cut short), the repositories and transaction steps send the migration back to rehearse again. The transaction reinstalls the rehearsal's databases over any later sync and uses its cache without syncing again and names each target in its repository, so a higher installed version is replaced. It must end with the packages the rehearsal ended with; file conflicts and free space are checked by pacman itself before it commits, which the rehearsal cannot do. A pacman lock left by a killed transaction is cleared only when no process holds it, and a transaction then runs to its end, even after a new rehearsal, so its hooks run. A candidate set is served to pacman as a local repository in the transaction's configuration only. Its key never enters pacman's keyring. An adapter can plan removals, rehearsed after the install and run by name after it, and can prepare the system just before pacman runs (restoring it when pacman fails), listing unowned files the transaction may overwrite.
- **Boot:** the stage-two image (m1n1, device trees, U-Boot) and the GRUB or Limine menu are rebuilt and checked with the boot check's pending-reboot mode before the loader changes. A Mac that booted GRUB at preflight is switched by `setup/limine-boot.sh`, which restores what it touched on failure, and a switch cut short runs again. After the reboot, `omarchy-mac-migrate-verify.service` (enabled on every run while a reboot is pending) requires Aurora running through the packaged Limine and a passing boot check of the boot chain (`--boot-chain`, as `update-verify` runs it). Retire writes the completion record first; its cleanup is repeated by any later run.
- **Legacy omarchy-mac:** a Mac is legacy when Omarchy is not a package, `omarchy-mac-keyring` is installed or the tree carries quattro's `omarchy-upgrade-to-quattro-mac`. Its packages are planned as a tester's, plus the checkout's own builds (`omarchy-keyring`, `ttf-jetbrains-mono-nerd-basic`) where an official repository carries them; `omarchy-mac-keyring` is removed after the install, so no populate trusts the fork key again. The engine drops `[omarchy-aarch64]` whatever its SigLevel and deletes the fork key. Just before pacman runs, the transaction step backs up the files the checkout's setup wrote that the new packages bring (pacman replaces them, or keeps a changed configuration file and writes `.pacnew`), then removes the links into a checkout (`/usr/share/omarchy`, `/usr/bin/omarchy-*`), resets `/etc/omarchy.conf` and drops a dev link's sudoers path; if pacman cannot run, all of that comes back. Everything is kept in `backup/converted/`, and a file another package keeps owning stops the migration at prefetch. The archives this reads are linked into the migration's cache. The checkout itself is never touched. Retire removes the fork's channel transactions and moves the `pacman.conf` copies its tools left that still say TrustAll into the backup; with preflight refusing TrustAll in any repository, included files too, and the switch rewriting `[omarchy]` and dropping `[omarchy-aarch64]`, no TrustAll is left anywhere in pacman's configuration. Encrypted legacy Macs unlock through busybox `encrypt`: they are refused, and so never receive the HOOKS baseline, until their boot switch (ticket 45). A 3.x checkout is refused until `omarchy-upgrade-to-quattro-mac` has run. `migrations/1788200000.sh` never adds `[omarchy-aarch64]` back to a Mac with a migration journal.
- **Refusals:** preflight exits 2, which leaves the upstream migration pending and stops the migrations after it (and the rest of `omarchy update`) until the reason is fixed: a low battery, too little space, incoherent boot files, an unfinished first boot or an untrusted repository. A kernel update waiting for its reboot is not a refusal.
- **Activation order:** the migration marks itself done the first time it runs. Wherever it runs before a target is set, it does nothing and never runs again. So the build that first carries the migration to users must also carry its target (ticket 53).
