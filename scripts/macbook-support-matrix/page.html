Apple Silicon MacBook support matrix

What the Omarchy Mac kernel (linux-aurora) and boot loader (m1n1) actually drive on every Apple Silicon MacBook: 42 boards from M1 to M6, including MacBook Neo. The board list comes from Apple's model pages and AppleDB, so models that have no code yet are included. Every cell comes from code: the compiled device tree for that board, a matching kernel driver, and any per-board gate in the driver or m1n1. A green cell means the code is there and enabled by default. It does not mean the feature has passed hardware testing.

Evidence

How a cell is decided

  • Each board's .dts is preprocessed and compiled, then every node's effective status is read (a node is off if it or a parent is disabled).
  • Each enabled node's compatible strings, or its PCI ID, are matched against drivers/ and sound/. All 27 trees bind a driver for every enabled device.
  • Per-board gates then override that: GPU admission tables, display board tables, the audio speaker table, and m1n1's defaults and handoffs.

GPU gates

  • OF matches: asahi/driver.rs:164-218 covers t8103, t8112, t600x, t602x, t8122, t6030, t6031, t8140; the G15 driver (g15/mod.rs:143-157) covers t6030, t6031 and t6034.
  • M3 Air / J504: asahi/m3/t8122_admission.rs:9 admits only J613, J615, J504.
  • M3 Pro: asahi/g15/glue.c:229 admits only J514S, J516S, and g15/hw.rs:156-171 pins one firmware TEXT for each. The 11-core CPU / 14-core GPU bin loads a different firmware (TEXT cd05af6a…), so its GPU is refused; linux-aurora#366 (J514S) and #390 (J516S) add it.
  • M3 Max: g15/hw/t6031.rs:183 is J516C. J514C is admitted by g15/boot.rs:475 (linux-aurora#363), which logs that its power values are inherited from the J516C and unqualified. J514M (T6034) is admitted by g15/boot.rs:479 (linux-aurora#408, with mesa#33); boot.rs:497 refuses every other T6034 board, so J516M stays off. m1n1 has no T6034 path until m1n1#32 merges.
  • m1n1 defaults: kboot.c:407-419 turns graphics on for J613, J615, J504, J514S, J516S, J516C and J514C (added by m1n1#31).

Display gates

  • M1/M2 families use the standard DCP driver (apple,t8103-dcp and successors).
  • M3 boards: drm/apple/iomfb_v14_7.c:231-239 lists T6030 (any M3 Pro), J613, J615, J504, J516C, J514C and J514M. J516M has no entry.
  • External displays: M3 Pro is native when the device tree's asahi,t6030-dispext = "1" handoff is present (dcp.c:1385). J613 needs chosen.asahi,t8122-dcpext=1 (m1n1 kboot.c:2785). Only t8122-j613.dts describes the USB-C routes to dcpext; J615 and J504 have none, so the switch does nothing there (J615 routes in linux-aurora#356). M3 Max has no external display nodes yet (linux-aurora#292). Neo is gated by dcp_h17p_external_supported (apple_drv.c:901).

Audio, Touch ID, Neo

  • Speakers: sound/soc/apple/macaudio.c:1862. Every MacBook config has speakers enabled, either directly or through a compatible fallback (M2 Pro to J314/J316, M3 to J314/J316/J413/J415). Speakers still need the speakersafetyd daemon in userspace.
  • Touch ID: the SEP driver (drivers/soc/apple/sep.rs) exposes enrol/verify through /dev/sep-bio. SEP nodes ship disabled by design and the driver enables them at runtime (sep.rs:10), so a board is covered when soc/apple/profile.rs:550-590 has a profile for it (T8103, T6000/T6001, T6020/T6021, T8112, T8140, and T8122 for J613/J615 only) and its fingerprint sensor node is enabled. That covers every M1, M1 Pro/Max, M2, M2 Pro/Max and M3 Air MacBook, and Neo. M3 Pro SEP is in linux-aurora#282. Touch ID still needs userspace integration.
  • Neo: Wi-Fi and Bluetooth use the MT7932 drivers. m1n1 disables Neo PCIe only if its PCIe setup fails (kboot.c:6693).

Power + sleep

  • Each cell gives code evidence first and lab results second, labelled "Code" and "Lab". Partial means the code paths exist but sleep is s2idle only and drains far more than macOS.
  • cpufreq: an enabled *-cluster-cpufreq node with a driver match (drivers/cpufreq/apple-soc-cpufreq.c). It is present on M1 to M3, Neo and J813. The M4 trees have none.
  • cpuidle: drivers/cpuidle/cpuidle-apple.c:173-186 starts on t8103, t8112, t8122, t600x, t602x, t6030, t6031, t6032, t6034 and t8140 (WFI only on T8140). It does not start on any M4, M5 or M6 chip.
  • s2idle: Apple Silicon has no PSCI system suspend, so mem_sleep offers only s2idle on every board. There is no S3-style deep sleep.
  • Display sleep: the DCP driver has system-sleep handlers for every generation (drm/apple/dcp.c:5086, apple_drv.c:1291). GPU: the GPU driver has no system-sleep callbacks; its firmware stays resident. On T6031, genpd powers the GPU domain off under it, which linux-aurora#288 fixes (open).
  • Lab: M1 Pro J314S figures are 5 V input measurements from 14 Oct 2026. The M3 Pro J514S figure is the SMC coulomb counter on battery, from linux-aurora#274. The M2 Pro figure is from the 9 Oct 2026 battery investigation. A live Thunderbolt link adds about 1.3 W in sleep on the M1 Pro.

M4 Pro and later

  • Board codes and chip IDs come from Apple's MacBook Pro and MacBook Air identification pages and AppleDB. The tree has no .dts for any of these 15 boards.
  • Chip-level code only: m1n1 soc.h defines T6040, T6041, T6050, T6051, T8142 and T8152. For T604x and T605x, m1n1 has only CPU start code (smp.c). The kernel has a G17 GPU config for agx-t6040 (asahi/driver.rs:168) but no T6040 device tree to use it.
  • M5 Max J714C: linux-aurora#404 adds T6050 and J714C. It covers CPUs, NVMe, keyboard, trackpad, keyboard backlight and SMC, with the panel as a framebuffer. It leaves out Wi-Fi/BT, sound, USB, GPU and the display controller. The m1n1 side is m1n1#30, #33, #34 (N1 Wi-Fi, opt-in), #37 (GPU) and #35 (display, opt-in).
  • M6 (T8152): the kernel has the Mac mini J873G device tree, CPU IDs and cpufreq, and m1n1 has display, DCP and ATC PHY code for the chip. All of it targets the Mac mini (linux-aurora#191 to #198, #359). The J804 MacBook Pro has no board file.
  • AppleDB gives M5 Pro and M5 Max the same chip ID (0x6050), while m1n1 also defines T6051. Whether the M5 Max splits across two chips, as the M3 Max did, is not confirmed.

The edge catalog column is the installer's model list. No M4, M5 or M6 MacBook is offered. J604, J713, J715 and J813 have device trees that describe CPUs and little else: there is no storage controller, so Linux has nowhere to install. The other 15 boards from M4 Pro onward have no device tree at all.

Not covered by code evidence: backlight and fn-key behaviour, sustained power and thermals. The 28 Oct test reports still fail display controller, backlight, ambient light, fn key and external display checks on every M3 board that reported.
